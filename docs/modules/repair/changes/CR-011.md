# CR-011 — Reporter ticket list and contextual detail redesign

Status: APPROVED (2026-10-18) with one owner change · applied in Stage 2N
Requested: 2026-10-18 by project owner
Size: M

## What changes

Redesign S06 and S07 using the owner-provided `support ticket1.png`, `support ticket2.png` and `timeline.png`. Pair them with the revised CR-010 neutral three-service shell. Standalone interactive proposals: `output/navbar-redesign/repair-my.html` and `ticket-detail.html`.

The user called the routes `/repair/me` and `/repair/ticket/[ticketID]`. The existing application routes are `/repair/my` and `/repair/tickets/[id]`; this proposal targets those existing screens and does not rename routes.

- S06 revised from the owner's new `myticket.png`: a white workspace with view tabs (by status / reported / following), pill filters for status/date/sort, search and compact tables grouped into awaiting evaluation, in progress and closed. Groups show counts and collapse independently. Dashboard statistic cards are removed. The current reporter's evaluation action is highlighted; subscribers only open details. Mobile renders the same groups as readable rows/cards. No staff metrics, bulk actions or editable statuses.
- Latest owner refinement: improve visual hierarchy without adding dashboard clutter. Add a small existing white-leopard bust beside the S06 page heading (never in global navigation), pale violet/blue/green group headers paired with icons and text, stronger issue titles, and a labeled violet review button. The heading links to the first actionable review only when the currently filtered results contain reporter-owned awaiting-evaluation work; hide it for loading/error/forbidden/empty states. This proposed mascot placement is explicitly requested for the preview and must be reconciled with the approved design-system placement rules before implementation.
- S07: clear issue title, ticket number, location, current step and expected finish at the top; one next-action panel driven by current step, viewer relation and existing allowed actions. Evidence and repair outcome follow. A vertical timeline uses solid completed markers, an outlined current marker and muted future steps, matching the supplied timeline reference.
- General users do not see priority/source, queue position, contractor identity/contact/rating, internal assignment controls or staff-only audit data. Reporter-facing expected-date changes, repair result, send-back reasons and closure reasons remain visible. Hiding UI fields does not change API authorization.
- Reporter/subscriber distinction is explicit. Only the reporter may evaluate/send back when authorized by the API. Subscribers see informational copy and no action buttons.
- Timeline preserves five approved stages and the conditional rework stage. Missing timestamps are not fabricated; anticipated finish dates say "คาดว่า". Automatic/admin/team closure is not described as a user evaluation.
- Loading, empty, filtered-empty, error, forbidden and not-found are included as interactive preview scenarios. Preview actions demonstrate feedback only and do not submit to the API.

## Why

The owner wants a modern UX that conveys context immediately and hides information irrelevant to general users. The latest S06 reference is `myticket.png`, which supersedes the initial dashboard/card direction: adapt its view tabs, pill filters and grouped tables to repair status groups. Earlier support-ticket references informed the first draft; `timeline.png` remains the S07 reference. References do not supply business rules or permission changes.
