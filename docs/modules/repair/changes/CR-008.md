## What changes

**A. Master data and priority (user point 1; answers 2026-10-16)**
- Categories and symptoms are maintained by the admin in `settings` S22 (already planned, settings Stage 5). Each **symptom** gets a priority; each **category** gets a default priority.
- The reporter **no longer picks priority**. Ticket priority = the highest priority of the picked symptoms. Only "อื่นๆ" symptom picked → the category's default. Category "อื่นๆ" → `medium` (ปกติ). Admin can still change it afterwards (F22).
- The reporter can type **"อื่นๆ"** for the category (then only a free-text symptom) and for the symptom (in addition to or instead of listed ones). Free text ≤ 100 chars.
- S03 shows the resulting priority read-only with the reason ("ระบบกำหนดจากอาการ “มีน้ำหยด” คุณไม่ต้องเลือกระดับเอง").

**B. New design direction for the whole app (user point 2; mood and tone approved 2026-10-16)** — replaces Option A (D-018)
- Look of `CR-008/demo.css`: light gray canvas, white panels with thin borders, no gradient headers, compact sections, data as label / value rows, no repeated information, Anuphan for all text.
- Token values (source for the `design-system.md` rewrite): `--blue #2741fa` · `--ink #182238` · `--muted #667085` · `--line #e5e8ef` · `--canvas #f6f7fa` · `--soft #eff2ff` · `--green #117653` · `--orange #b75016` · `--red #c33432` · `--violet #7543c5` · panels radius 16px, controls 8px, touch targets ≥ 44px. Status / priority colors keep their meaning.
- Mascot only on success / empty / forbidden screens. `docs/shared/design-system.md` is rewritten; every built screen is restyled.

**C. S03 report form (user point 2.1; layout from design demo 04, UX round 5)**
- One page, compact sections: **ปัญหาที่พบ** (category buttons, symptom check boxes, priority explanation, optional details) · **สถานที่เกิดปัญหา** · **รูปภาพ** · (leads in team mode) **ทีมทำอะไรไปแล้ว**. Each section shows "ครบแล้ว" when its required fields are valid. Desktop: summary "ตรวจข้อมูลที่กรอก" + footer with what is missing and the submit button; phones: a sticky bottom bar with the same text and button. The submit button is never disabled; errors list links to the sections.
- **Photo first on phones (≤ 600px):** the photo section comes first with "ถ่ายรูป" (camera capture) and "เลือกจากคลังรูป" — the reporter is standing at the problem and the photo is required (BR-F02-1). Desktop keeps ปัญหา → สถานที่ → รูป with a drag-and-drop upload zone (photos usually sit on the phone). DOM order follows the visual order.
- **ที่เคยแจ้ง:** the reporter's last 3 distinct places (building · floor · room) as one-tap shortcuts that fill the selects; **never preselected** (a silent wrong default sends the technician to the wrong floor). First-time reporters see only the selects.
- **QR entry** (`?asset=`, F13-B): banner with the asset; category and place prefilled; "ไม่ใช่อุปกรณ์นี้" removes the asset and keeps the values.
- **Duplicates while filling (F03, rule BR-F03-1 unchanged, only the timing):** as soon as category + building + floor are known, open tickets on that floor in that category appear under the place section, newest first:
  - someone else's → "ติดตามงานนี้แทน" (the form's photos and details are added to that ticket, BR-F03-3)
  - the reporter's **own ticket waiting for their rating** → "ส่งกลับให้แก้ในงานเดิม" (opens S07 `?action=sendback`) instead of a second report
  - the reporter's own ticket in another step → "ดูงานของคุณ"
  - "ไม่ใช่เรื่องเดียวกัน แจ้งต่อ" hides the card (undo link stays). Submitting while a duplicate is still undecided opens **S04 as a dialog** (fallback).
- **Team mode** (housekeeper / security leads, F04): segmented "ให้ช่างซ่อม | ทีมแก้เองแล้ว" above the form; team mode adds the section "ทีมทำอะไรไปแล้ว" (what the team did + after photos, required, BR-F04-2), the title / button "บันทึกงานทีม" and still runs the duplicate check (BR-F04-3).
- **Draft:** the form is saved in the browser while typing and restored with "กู้ข้อมูลที่กรอกค้างไว้เมื่อ … แล้ว" + "เริ่มใหม่" (covers a reload after switching to the camera app). Photos survive through their upload ids (D-022 keeps unattached uploads 24 h). Draft key includes the employee code and is cleared on submit / logout.
- **S05 success page:** mascot, ticket number + copy, 4-step mini progress (แจ้งซ่อม done · ช่างรับเรื่อง next), "ต่อไป" box (the technician will set the expected date, we notify you, priority + why), short summary, "ดูงานนี้" / "แจ้งเรื่องอื่น". Variants: team (closed at once; how to hand over later, F05) and follow (your photos were added; the original reporter rates).

**D. S07 ticket detail (user point 2.2; layout from design demo 04, UX round 5)**
- Header: ticket no + copy, status badge, title, reported time, "พิมพ์รายงาน". A **next-action band** under it says what is happening, what the viewer should do and by when, with the actions.
- ข้อมูลงาน: the room as the headline (+ building / floor), category, asset, priority + reason, expected / done date; people: reporter (+ follower count) and fixer (ช่างของบริษัท / ช่างภายนอก; reporters see only the contractor type, BR-F06-4).
- **รายละเอียดและผลการซ่อม:** before / after side by side with photo lightbox (phones: ก่อนซ่อม | หลังซ่อม toggle); before the repair is done only "ก่อนซ่อม" in one row; send-back reason and rating result under it. Pattern: side-by-side before / after photos tied to the work order (Property Inspect, Zuper, FloorZap).
- **Timeline** = 4 stages (แจ้งซ่อม · ช่างรับเรื่อง · ซ่อม · ให้คะแนนและปิดงาน), plain copy (done "…แล้ว", current "กำลัง… / รอ…", future = what will happen), "สิ่งที่ต้องทำต่อ" box with the auto-close time, "ดูประวัติทั้งหมด" log. Carbon progress indicator states; GitHub Primer condensed items.
- **Wording:** "ประเมิน" meant two things — technician side becomes "รับเรื่อง", reporter side "ให้คะแนน" (button "ประเมินงาน" → "ให้คะแนน"); "ช่างในระบบ" → "ช่างของบริษัท". Applies to S06 / S07 / S08 / S17 / notifications.
- **Viewer-aware band (round 5)** — the same page for every role, actions from `allowedActions`:
  - reporter: per step (waiting for the technician → nothing to do yet; in repair → expected date and why it moved; waiting for rating → stars + "ส่งกลับให้แก้" + auto-close deadline)
  - follower: "คุณติดตามงานนี้", no actions, "ผู้แจ้งเป็นคนให้คะแนนเมื่อซ่อมเสร็จ"
  - technician: "รับเรื่อง" (new) · "เลื่อนวันเสร็จ" + "บันทึกผลซ่อม" (in repair) · "กำหนดวันใหม่" + "บันทึกผลอีกครั้ง" (sent back) · waiting / closed info
- **Quick rating (round 5):** five stars right in the band; tapping one opens S08 with that score. **No preselected score** (demo 04 started at 5 stars, which inflates scores — CR-005 wants many honest ratings, D-040). Label per score; 1–2 stars → "ยังไม่เรียบร้อยใช่ไหม? ส่งกลับให้แก้แทนได้" with a button that switches to send back. Rating is still required to confirm (BR-F07-2).
- **Technician sheets (round 5, S17 / S10)** — built for one hand on a phone:
  - **รับเรื่อง:** date chips วันนี้ · พรุ่งนี้ · อีก 3 วัน · เลือกวัน (native date, today or later) + ใครซ่อม ช่างของบริษัท | ช่างภายนอก (picker + "เพิ่มช่างภายนอกใหม่" → S18 form without leaving)
  - **เลื่อนวันเสร็จ / กำหนดวันใหม่:** the same sheet + **optional reason shown to the reporter** ("เหตุผลที่เลื่อน", ≤ 100, new)
  - **บันทึกผล:** the reporter's before photo next to the after-photo camera tile ("ถ่ายมุมเดียวกับรูปก่อนซ่อม"), what was done, contractor score for contractor jobs (BR-F24-3)
- **Print report:** browser print (`@media print`), A4: header, job info, people, before / after, history table, sign-off lines.
- Deep links `?action=sendback|confirm` (used by the form's duplicate card and by notifications).

**E. Superadmin (user point 2.3)** — the user approved the settings screens and plan (2026-10-16) with the new style. Settings mockups are restyled when each settings stage is prepared; S22 adds the priority fields from A (tagged CR-008).

**F. Dashboard S27 ภาพรวมองค์กร (user point 2.4; design demo 04, unchanged in round 5)** — replaces S12 ภาพรวมอาคาร 3D.
- Building names (user): อาคารหลัก → **อาคารฝั่ง Office**, อาคารด้านหลัง → **อาคาร Office โรงงานบางซ่อน**.
- KPI tiles that open their list: งานที่ยังไม่ปิด · รอช่างรับเรื่อง · ฉุกเฉิน / ความเร่งด่วนสูง · เกินวันที่คาดว่าจะเสร็จ; scope filter (ทุกอาคาร / per building).
- **Isometric 2.5D campus** (SVG, rotate 90°, no 3D library, D-025 kept): floors coloured by the highest open priority with counts; pick a floor → its tickets in the side panel and "ดูผังห้องชั้นนี้" (rough room plan per floor with tickets per room); list view by floor as the accessible alternative.
- "สิ่งที่ควรติดตาม" (critical + overdue), 7-day "งานเข้าและงานที่ปิด" chart with a table, services panel (cars / rooms = **mock with "ตัวอย่าง"**, repair satisfaction 30 days). Loading / error / forbidden / empty states.

## Why

User request 2026-10-16: the reporter should not guess urgency; the admin owns the rules; screens looked busy and repeated data; one picture of the whole site that links repair, parking and rooms.

Round 5 (context, from `01-users.md`): the **reporter** uses the app rarely, on a phone, standing at the problem (photo / QR first, one-tap place, no learning, never a second report for the same thing); the **technician** is one person working all day on a phone with busy hands (date chips instead of typing, photo next to the before photo, next step always visible); **leads** record work their team already fixed while walking the floor; the **admin** works at a desk (dashboard unchanged). Sources: Snap Send Solve help (photo-first report, up to 5 photos, close-up + wide shot), Baymard accordion checkout study (summaries of what was entered, Back must not lose data), plus the round-2 sources above.
