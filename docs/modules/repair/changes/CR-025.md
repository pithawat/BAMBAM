2. Every building has a **building type** (from a building-type table). Every category says which building types it is used in. ปัญหาที่พบ shows only the categories of the chosen building's type.
3. Admin and Superadmin set the building types of a category when they add / edit it (settings S22), set a building's type (settings S20) and manage the building-type list.

### Design

**Data.**
- New table `platform.building_types` (id, name ≤ 100 unique ignoring case, sort_order, is_active, timestamps, `updated_by_id`) — next to `platform.buildings` (moved there by settings Stage 4, migration `20261026000003`).
- `platform.buildings.building_type_id` — **required** (NOT NULL, FK).
- `repair.category_building_types (category_id, building_type_id)` — the building types a category is used in (an allow list).
- The `isOther` category `อื่น ๆ` is used in every building type and needs no rows (always shown, cannot be limited), so every place always has a valid choice. `อาการอื่นๆ` (typed) stays available in every category.
- Rules are per **category** only; symptoms follow their category (the owner asked for category level; the earlier symptom-level idea is dropped).
- Room area types (CR-014) stay as they are; no new area types. The CR-014 hint `repair.category_area_types` ("rooms matching the category show first") no longer makes sense once the place comes first → retired: S03 lists rooms in their normal order, the table is dropped and `areaTypes` leaves #1.

## Why

Reporters pick the problem first and then the place, so they can report things that cannot exist there (แอร์ในพื้นที่ภายนอกอาคาร, แอร์ในโกดัง). Choosing the place first and tying categories to the building type shows only problems that make sense, which is shorter for the reporter and cleaner data for the technician. A building-type table keeps it to one setting per type instead of per building.
