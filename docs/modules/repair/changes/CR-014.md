# CR-014 — Real category / symptom master, equal wizard frames, required room from a master

Status: PROPOSED
Requested: 2026-10-19 by project owner
Size: L (proposed)

## What changes

Owner's words (Thai, summarised):

1. Use the category / symptom list in `attachments/REPAIR-CATEGORY-SYMPTOM-MASTER.md` in the report form (S03).
2. Every wizard step uses the same card size / frame (no width or height jump between steps).
3. "ห้องหรือจุดที่เกิด" becomes required and is tied to master data, so reporters cannot type odd places. Owner asked for a design recommendation.
4. Categories and symptoms live in the database; admins add more later.

### Proposed design

**1 — Master data (7 categories, 42 symptoms).** Load the attachment through a goose data migration (runs in every environment, not only the dev/UAT sample seed). Old sample categories / symptoms (`seed.go`) are set `is_active = false`, never deleted (tickets keep their references). Selection rules from the attachment: 1 category, ≥ 1 symptom, changing category clears symptoms and the typed "อื่นๆ" text (already the behaviour).
- Each category's last item `อื่นๆ` / `อื่นๆ โปรดระบุ` is **not** a symptom row; it is the existing `symptomOther` check box (`อาการอื่นๆ` → `ระบุอาการอื่นๆ *`, ≤ 100).
- Category 7 `อื่น ๆ` becomes a real DB category with its 4 symptoms, flagged `is_other = true` (one per system, cannot be deleted / deactivated by the admin). The client-side "อื่นๆ" card is replaced by this DB category. Picking it shows `ระบุหมวดงาน (ไม่บังคับ)` ≤ 100 — the typed name is stored in `categoryOther` as a value **under** that category (`categoryId` = the อื่น ๆ category, never null for new tickets). `categoryOther` is rejected for any other category. (Owner answer Q2, 2026-10-19.)
- Every symptom needs a priority (CR-008, BR-F02-2). The attachment has none → the table below is used (owner answer Q3, 2026-10-19). When an admin adds a category (settings S22) the category default priority and every symptom priority are **required**, and priorities stay editable for every category, including the seeded ones.
- Icons: lucide names per category (`zap`, `snowflake`, `droplets`, `presentation`, `building-2`, `square-parking`, `ellipsis`).

**2 — Equal frames.** One content width on desktop for every step (proposed 880px instead of 1040 / 720) and one minimum card height (the tallest step on desktop, about the ปัญหาที่พบ step), so the progress strip, card edge and sticky footer never move. Mobile: full width already; card keeps `min-h` = viewport minus header / footer.

**3 — Required room from a master (recommendation).**
- `platform.rooms` per floor (already planned by settings Stage 4, D-048) is created now. Each room has a name and an **area type** (`meeting_room`, `restroom`, `office`, `common_area`, `parking`, `pantry`, `other`).
- Each category lists the area types it usually happens in (`repair.category_area_types`), e.g. ห้องประชุมและโสตทัศนูปกรณ์ → meeting_room; ลานจอด / ไม้กั้น → parking; ประปาและสุขาภิบาล → restroom, pantry.
- S03 สถานที่: `อาคาร *` → `ชั้น *` → `ห้องหรือจุดที่เกิด *` = room cards of that floor; rooms matching the category show first under `ห้องที่ตรงกับปัญหา`, the rest under `ห้องอื่นบนชั้นนี้` (shown, not hidden — the mapping is a hint, not a block). Every floor gets one `พื้นที่ส่วนกลางชั้น {n}` room so there is always a valid choice.
- Optional `บอกจุดเพิ่มเติม (ไม่บังคับ)` ≤ 100 (e.g. `ฝั่งหน้าต่าง`) keeps the old `locationDetail` for precision; the place itself is never free text.
- Server: `roomId` required, must be active and belong to the floor → else `MASTER_DATA_CHANGED`. Duplicate check (CR-009, Stage 4) matches by `roomId` instead of trimmed text. ที่เคยแจ้ง (#28) returns rooms.
- Parking: ลานจอด has no building / floor today → needs a building entry such as `พื้นที่ภายนอกอาคาร` with zones as "floors" (open question).

**4 — Admin adds later.** Categories / symptoms already are DB tables (`repair.categories`, `repair.symptoms`); the admin screens stay where planned: settings S22 (settings Stage 5) for categories / symptoms / area types / priorities and S21 (settings Stage 4) for rooms + area type. Until those stages, the master changes only by migration (owner answer Q4, 2026-10-19).

Owner answers 2026-10-19: Q1 room from master + linked to category (recommended) · Q2 DB category อื่น ๆ + optional typed name as its value · Q3 proposed priorities; required when an admin adds a category, editable for all · Q4 admin screens as planned.

## Why

The sample categories were placeholders (PROGRESS Open issues: "real seed files"); the owner now supplied the real list. Free-text places make tickets hard to find, group and de-duplicate, and let reporters type anything. Frames that change size between steps feel jumpy.
