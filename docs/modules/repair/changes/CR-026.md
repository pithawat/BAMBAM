# CR-026 — Compress uploaded photos harder (25 %)

Status: APPROVED (2026-10-27) · amendment A1 (photos stay in the form until submit) APPROVED 2026-10-29 (option A)   <!-- PROPOSED → APPROVED → DONE (or REJECTED) -->

## What changes

Owner's words (Thai): "บีบอัดไฟล์รูปให้เหลือความชัด 25%"

Today (D-022, `frontend/src/modules/repair/api.ts` `resizeForUpload`): every photo is resized in the browser to a long edge of **1920px** and saved as **JPEG quality 0.85** before upload; the server stores it as is and makes a 480px / quality 80 thumbnail (`photostore.go`).

Proposal: JPEG quality **0.85 → 0.25** for every upload through `PhotoPicker` (S03 report, S04 follow, S08 send back, S10 resolve — one shared function), long edge stays 1920px. Thumbnail unchanged.

"ความชัด 25%" can mean three different things — to confirm (Q1):

| Reading | Change | Effect (rough, depends on the photo) |
|---|---|---|
| A. JPEG quality 25 % (recommended reading) | `RESIZE_QUALITY` 0.85 → 0.25 | file roughly ¼–⅓ of today; full size, visible blockiness on fine detail (text on labels, thin cracks) |
| B. File size ≈ 25 % of today | step quality down until the file is ≤ 25 % of the 0.85 version | same goal as A but predictable size; slower on old phones |
| C. Resolution 25 % | long edge 1920 → 480px | very small files; zooming into the photo is no longer useful for the technician |

Claude recommends A, and to look at 2–3 real repair photos at 0.25 / 0.4 / 0.6 before fixing the number (a side-by-side sample page can be made from photos the owner supplies).

## Why

Smaller files: faster upload on mobile data, less storage on `PHOTO_STORAGE_DIR`, faster S07 / S29 loading.

Risk / notes:

- Only the browser compresses. Files the browser cannot decode (HEIC on some desktop browsers) are uploaded unchanged — today's behaviour; a server-side re-encode would cover them but needs a HEIC decoder in Go (Open issues already lists "HEIC has no server thumbnail"). Not proposed now.
- Quality 0.25 is low for evidence photos (meter readings, model plates, hairline cracks). If the technician needs detail, 0.4–0.5 halves the size with much less loss.
- Size M only because it touches finished stages; the change itself is one constant + docs (D-022 superseded by a new D-###).

## Amendment A1 — photos stay in the form until submit (APPROVED 2026-10-29, option A)

Owner's words (Thai): "ทุก form ที่มีการแนบรูปให้เก็บรูปไว้ในฟอร์ม ไม่ต้องเก็บไว้ที่ server ก่อน"

**Today (D-022):** `PhotoPicker` uploads each photo to #3 right after picking; the form keeps only the returned id and sends `photoIds` on submit. Photos of abandoned forms stay on the server until the 24 h purge. Drafts (S03, CR-008) keep the ids, so a refreshed page gets its photos back.

**Proposed:** picking a photo only resizes it (1920px, quality 0.25) and keeps the **file in the browser**; the tile shows a local preview. Nothing reaches the server until the user presses the form's submit button. On submit the form uploads its photos, then sends the action with their ids.

| Option | How submit works | Contract | Notes |
|---|---|---|---|
| **A (recommended)** | upload each kept photo with #3 (progress `กำลังส่งรูป 2/3…`), then call the action (#5 / #9 / #10 / #23) with `photoIds` | **unchanged** | retry re-uses photos already uploaded in this attempt; a failed submit leaves at most a few unattached uploads, removed by the existing 24 h purge |
| B | one `multipart/form-data` request per action (fields + files) | #5, #9, #10, #23 (+ team handled) change to multipart; #3 only for… nothing | atomic, no orphans; bigger rewrite of 5 endpoints + Go tests |

**Forms affected (every PhotoPicker):** S03 report (+ team mode `รูปหลังทำ`), S04 follow (#23), S08 send back (#9), S10 record result (#10). Settings has no photo upload.

**Drafts (S03):** to keep the CR-008 rule "refresh after switching to the camera keeps what was filled", the resized photo files are stored in the browser (IndexedDB, per user and per mode, ≤ 5 × ~0.3 MB) with the draft and removed on submit / `เริ่มใหม่` / logout. If the browser blocks storage, the draft restores without photos and says `แนบรูปอีกครั้ง` (same as mock mode today). Other forms (S04 / S08 / S10 dialogs) have no draft — closing them drops their photos (as today they leave unattached uploads).

**Edge cases.**
- Upload fails during submit → `ส่งไม่สำเร็จ ลองอีกครั้ง`; form data and photos stay; the failed tile is marked.
- A photo that the server refuses (type / size) is shown on its tile at submit time instead of at pick time; type and the 10 MB limit are still checked in the browser at pick time.
- Duplicate check (CR-009 / CR-021) and every other check run before the photos are uploaded, so a blocked report uploads nothing.

Size stays **M** (option A) · option B would be **L** (contract of 5 endpoints).

Owner answers 2026-10-29: option **A**. Why A is safe (owner asked whether photos can go missing): the action (#5 / #9 / #10 / #23) attaches the photo ids inside the same DB transaction as the ticket / event; an unknown or expired id fails the whole request (`PHOTO_NOT_FOUND`) and nothing is created. So a ticket never exists with missing photos — the only leftover of a failed submit is unattached uploads, which the existing 24 h purge deletes (no one has to check them). Option B would give the same result for the ticket with a much bigger contract change.
Draft photos in IndexedDB get a **24 h expiry** (owner request): every entry keeps `savedAt`; entries older than 24 h are deleted when the app starts and when a form opens (browsers have no background timer for this). Size on the device: ≤ 5 photos × ~0.2–0.3 MB at 1920px / quality 0.25 per draft, at most one draft per mode per user → about 1–3 MB, negligible. Stage: moved with the quality change into repair **Stage 4P**, which now runs before 4R (D-121).
