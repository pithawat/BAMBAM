# SSO — configuration and integration

Source: `bam-sso-handoff.md` (generated by RMC SSO Admin, repo root, **gitignored because it contains the Client Secret**).
This file is the single source for agents. It never contains secret values.

## Provider

RMC SSO · OIDC Authorization Code Flow + PKCE (S256 only) · confidential client (`client_secret_post`).
Upstream identity providers allowed: Microsoft Azure, LINE (no default provider).
The application creates its **own** session after validating tokens; internal APIs use that session.

## Flow

1. Browser opens BAMBAM without a session → login page (no auto-redirect, so logout cannot loop).
2. "เข้าสู่ระบบ" → server creates `state` + `code_verifier` (httpOnly, secure, sameSite=lax cookies) → redirect to Authorize with `code_challenge` (S256).
3. RMC SSO → `GET /api/auth/callback/rmc-sso?code&state` on the **frontend origin**. Check `state`.
4. Server exchanges the code at the Token endpoint (`client_secret_post` + `code_verifier`). Never in the browser.
5. Validate `id_token` (below), call UserInfo with the access token and check `sub` matches.
6. Upsert `platform.users` from claims, load the user's role from BAMBAM (D-003), create the app session cookie (httpOnly).
7. Logout: clear app session → redirect to End Session with `client_id`, registered `post_logout_redirect_uri`, `state` → public `/signed-out` page that does **not** start login automatically.

Stack (D-026, decided in Stage 0): Next.js rewrites `/api/*` to the Go backend, so Go owns login start (`GET /api/auth/login?next=`), the callback (`GET /api/auth/callback/rmc-sso`) and logout (`POST /api/auth/logout`), and sets the httpOnly session cookie on the frontend origin. Code: `backend/internal/platform/auth`. `state` + PKCE verifier + `next` travel in a 10-minute HMAC-signed httpOnly cookie (`APP_SESSION_SECRET`). App session TTL `APP_SESSION_TTL` (default 12h), no token refresh; SSO tokens are not stored.

### id_token validation — mandatory missing-`iss` compatibility

Signing is legacy **HS256**, verified with the client secret. RMC SSO may issue `id_token` **without `iss`**. Accept such a token only when all of these pass:
- signature verified (never trust a decoded payload)
- `aud` equals or contains `bam`
- `exp` present and not expired; `iat` checked when present; leeway = `SSO_CLOCK_SKEW` (default 60s, D-037)
- `sub` present and equal to `sub` from UserInfo
- `state` and PKCE verifier checked as usual
- if `iss` **is** present: normalise trailing slash and require exactly `https://rmc-sso.cipcloud.net`, else reject
- missing `iss` allowed only for this provider; log a structured warning (no token, no PII)

Never: disable signature/aud/exp checks, accept a mismatching `iss`, inject `iss` into the payload, or make this a global bypass.
Remove the exception once RMC SSO moves to JWKS/RS256 with `iss` always present (then verify via JWKS).

## Claims → app user

| Claim | Stored as (`platform.users`) | Note |
|---|---|---|
| `USER` | `employee_code` (unique) | the user key; roles are bound to this (D-003) |
| `FIRSTNAME_TH`, `LASTNAME_TH` | `first_name_th`, `last_name_th` | display name in UI |
| `FIRSTNAME_EN`, `LASTNAME_EN` | `first_name_en`, `last_name_en` | for EN UI later |
| `EMAIL` | `email` | |
| `DEPARTMENT`, `DIVISION` | `department`, `division` | shown on profile and tickets |
| `POSITION_TH` | `position_th` | shown on profile |
| `LINE_USER_ID` | ✏️ store only if LINE notifications are approved | personal data — do not store "just in case" |
| (role) | **not from SSO** → `platform.user_roles` | first login = `employee`; others set by seed (phase 1) then admin (F15) |

Refresh claims on every login. Store only claims the app uses.

## Must / must not

- Never commit or log the client secret, `id_token`, access/refresh tokens, or whole claim payloads.
- Tokens never in localStorage. App session in an httpOnly cookie.
- Logout must call End Session after clearing the app session.
- Redirect URIs must match the registration exactly, including trailing slash.
- When the client secret rotates, update the env var and RMC SSO Admin together.

## Maintenance guard (required before production)

- Server polls `GET …/api/maintenance/status?client_id=bam&environment=<env>` at least every minute (cache ≤ 1 min); phase `online | notice | maintenance`. During maintenance block important requests and show a maintenance page; if SSO is unreachable, keep the last seen maintenance state.
- For logged-in users the server calls `…/api/maintenance/access` with the user's access token (server side only); `allow=false` → block writes, show maintenance page.
- Expose `GET <home-url>/health/ready` on the home origin: requires `Authorization: Bearer <SSO_CLIENT_SECRET>`, returns `200 {"ready": true}` only when core dependencies are up. HTTPS in production.

## How to test locally

- Real login: DEV client `bam` against `http://localhost:3000` with a real RMC SSO account.
- Role preview without real accounts per role: dev/UAT role switcher logs in as seeded demo users (D-005, see architecture.md).
- Load tests (staging only): RMC SSO synthetic sign-in endpoint, enabled by the SSO team; never in production.
